## 1. Introduction

### 1.1 Purpose
This document collects the policies, privacy/compliance obligations, and computational formulas that govern how BookBuddies must operate as an application — independent of any particular screen or feature design — so that the specification can cite them rather than restate them.

### 1.2 Scope

This version covers rules that could be attributed to Yang Yang's concept brief, the BookBuddies Profiles notes, and the PM Core Experience deck. The COPPA rules (`BR-coppa-*`) are attributed to the FTC's amended COPPA Rule text, the document the client supplied, in [../coppa/coppa-full](../coppa/coppa-full); the team's engineering reading of it is in [../coppa/coppa-design-requirements.md](../coppa/coppa-design-requirements.md). It does not cover the product/UX decisions documented in the PM deck under the heading "PRODUCT DECISION" (e.g., using a rules-only recommender for v1, treating the Shelf as non-tracking, making typed comments optional) — those are choices the team made and can renegotiate, so they belong in the specification, not here

## 2. Rules

### 2.1 Account and Profile Structure

**BR-user-roles:** BookBuddies has two end-user roles, parent and kid, plus the system admin. There is no teacher role. Source: Meeting 2 notes, "Scope Simplification: Dropping Teacher Layer."
**BR-parent-account-linked:** A child account must be linked to a parent account. Source: client concept brief, "Parental Controls, Privacy, and Account Structure" section; confirmed in Meeting 2 notes, "Parent and Kid Roles." (v0.2: account-creation flag resolved by BR-parent-creates-kid-account.)
**BR-parent-creates-kid-account:** Only a parent may create a kid account; a kid may not self-register. The parent creates the child profile and enters the child's onboarding information. Source: Meeting 2 notes, "Parent and Kid Roles"; MTG2 flowchart deck, slide 1 ("Kid onboarding (set up by Parent)") and slide 3.
**BR-parent-account-structure:** A family has one primary parent account; a secondary parent may be added, and one parent account may manage multiple kid accounts. Source: Meeting 2 notes, "Parent and Kid Roles."
**BR-kid-anonymous-profile:** A child's profile must use a nickname and character avatar only; no real identifying information is displayed on the child's profile. Source: client concept brief, "Parental Controls, Privacy, and Account Structure" section. (v0.8 note: the system no longer stores the child's real name at all (see BR-kid-data-stored); the nickname is the child's profile name.)

**BR-kid-data-stored:** The system stores about a child only the items in the table below, each for the purpose given and for no other use (`BR-coppa-minimization`). Every item is personal information under the COPPA Rule once it is tied to the child's internal child ID, so none is collected before the parent's consent is confirmed (`BR-coppa-parental-consent`), each is named with its purpose in the notice (`BR-coppa-notice`), and each is kept only as long as `BR-coppa-retention` allows. **Never stored:** the child's real or legal name, any email, phone number or other contact detail for the child, a handle that works as contact information, free text written by the child (`BR-child-structured-responses`), a photo, video or voice recording, location, a biometric, or a government ID number. Source: client answers 2026-10-28, Q3, Q14 and overall comment 4 (`docs/external/client-answers-10-28-2026.md`), which replace the Meeting 2 notes, "Costs, Compliance, and Next Steps," that stored the real name for law-enforcement reporting (`OI-23` is closed); what counts as personal information from 16 CFR 312.2 and the minimization and retention duties from 312.7 and 312.10 (`docs/coppa/coppa-full`, `docs/coppa/coppa-design-requirements.md` §2–3).

| Item | Purpose | Who sees it |
|---|---|---|
| Nickname, avatar | The child's profile name and picture on child screens (`BR-kid-anonymous-profile`) | Child, parent |
| Internal child ID | Links the child's data over time without a name (client answers Q3, Q14); the key of every record below | Never shown to the child; the admin only through the lookup in `UC-ADM-view-usage-stats` |
| Username, password (stored only as a salted hash) | The child's sign-in (`KD-auth-sessions`) | Parent sees the username; the password is never readable |
| Age, grade | The main signal for recommendations (`BR-reading-level-proxy`); see Flagged | Parent |
| Reading level (optional, parent-entered) | An optional difficulty input (`BR-reading-level-parent-entered`) | Parent only, never the child |
| Reading interests, favorite books already read | The recommender's starting profile (`UC-REC-kid-onboarding`) | Child, parent |
| Interest profile (derived) | The strength of each interest, built from the child's choices, ratings and shelf activity; drives recommendations and the child's dashboard (`UC-SHLF-kid-dashboard`) | Child, as a chart with no numbers; parent; admin only through the lookup |
| Recommendation batches, reactions, decline reasons | The recommender learns from them; the parent reviews them (`UC-REC-parent-review`, `UC-REC-kid-review`) | Child, parent; admin only through the lookup |
| Shelf entries and shelf history (adds, moves, confirmed finishes, with times) | The shelf and the dashboard history; parent oversight (`UC-SHLF-kid-view-shelf`, `UC-SHLF-parent-view-shelf`) | Child, parent; admin only through the lookup |
| Ratings | The recommender and the shelf (`UC-SHLF-kid-rate-book`) | Child, parent; admin only through the lookup |
| Parent note | Optional context for the recommender (`BR-parent-note`) | Parent; the admin only if the note is flagged (`BR-note-safety-flagging`) |
| Shelf requests, reports and per-child exclusions, in-app notices | Parent approval, `BR-parent-report-book`, alerts (`CI-in-app-alerts`) | Parent; the child sees only the notices addressed to them |
| Usage records (sign-in, and meaningful actions with times) | The V1 engagement measures (client answers Q14: day-30 retention, weekly active families) and the admin's lookup | Admin, as aggregates or through the lookup |

Flagged — age and grade were not addressed in the 2026-10-28 answers, and the COPPA Rule bars collecting more than is reasonably necessary (`BR-coppa-minimization`), while `BR-reading-level-proxy` uses both; confirm with the client that both stay (`OI-29`). Per-child session length (client answers Q14) is not stored until a purpose and a retention period are set. An IP address or device identifier is itself personal information (16 CFR 312.2, "Personal information" (7)), so sign-in and session records must not keep one beyond what security needs. The export and deletion use cases must cover every row (`UC-PAR-review-child-data`, `UC-PAR-delete-child-data`, `UC-PAR-delete-kid-account`, `FR-DATA-removal`).
**BR-admin-limited-view**: The system admin may see parent account credentials and the number of child accounts under each parent, but not the child's details. "Credentials" means the Main Parent's and any Sub Parent's name, username and email, never a password (team clarification, 2026-10-26). Source: Meeting 2 notes, "Costs, Compliance, and Next Steps"; client answers 2026-10-28, Q5, agreed the default that the admin sees no child details and has only the access necessary. **Child-level usage data (client answers 2026-10-28, Q5, Q14):** child details are not the same as usage data. An authorized admin may look at one child's engagement and usage data, such as reading interests, recommendations and responses, shelf activity and ratings over time, by the child's internal ID, and never with a name or other identifying detail. The lookup is in `UC-ADM-view-usage-stats`, and each one is recorded in the audit log. **Exception (team position, 2026-10-26; client to confirm, `OI-15`):** in flagged-content review (`UC-ADM-flag-review`), and nowhere else, the admin sees the flagged parent note and the flagged child's nickname, internal child ID, age, grade and username, and every view is recorded (the client agreed that flagged-note access is limited to authorized users, and asked about a basic access log, which the audit log provides). Ask Yang Yang to confirm the exception.

**BR-coppa-parental-consent:** Verifiable parental consent must be obtained before the system collects, uses or discloses any personal information from a child, which in practice means at parent account creation and before any child profile is created or the child enters anything. The method must be reasonably calculated to confirm the person consenting is the child's parent, so a checkbox alone does not qualify. Email with an additional confirming step ("email plus") is acceptable only while the system does not disclose children's personal information to third parties or make it public; if that changes, a stronger method is needed. Each consent is recorded with date, method, and the version of the notice shown. Any material change to what is collected, how it is used, or who receives it needs fresh notice and consent. The COPPA Rule text has no school-consent exception (the FTC proposed one, did not finalize it, and says it keeps enforcing under its existing guidance, which is not in the rule text), so the product has the parent consent and does not let a teacher or school consent in their place. Source: client ("COPPA compliance: build in from the start," Meeting 2 notes, "Costs, Compliance, and Next Steps"); rule content from the FTC COPPA Rule, 16 CFR 312.4–312.5, the document the client supplied (`docs/coppa/coppa-full`). Flagged — the consent method is not yet formally chosen (`OI-21`). The client accepted parent consent, email confirmation, a consent record and revocation for V1 on 2026-10-28 (Q13), and asked that the process stay configurable because testing and legal review before a broader release may change it.

**BR-coppa-notice:** Before consent, the parent must receive a direct notice, written clearly and with no unrelated material, that states: consent is required and nothing is collected without it; what personal information is collected and how each item is used; whether any third party receives it (named or by specific category, with the purpose); that the parent may consent to collection without consenting to disclosure; a link to the online privacy notice; and how to give consent. If the system holds a parent's or child's contact details only to obtain consent, the notice must say they are deleted if consent is not given within a reasonable time. The online privacy notice must be linked from the home screen and at every place personal information is collected from a child, and must state the operator's contact details, the information collected, disclosure practices, the retention policy (`BR-coppa-retention`), and the parent's rights (`BR-coppa-parent-rights`). Source: FTC COPPA Rule, 16 CFR 312.4 (`docs/coppa/coppa-full`).

**BR-coppa-parent-rights:** On request, a parent must be able to see what categories of personal information are held about their child and to review the actual data, to refuse any further use or future collection, and to have the child's data deleted. The system must confirm the requester is that child's parent and must not make this unduly burdensome. "Deleted" means no longer retrievable in the normal course of business. The system may end service to a child whose parent has refused collection or required deletion. Source: FTC COPPA Rule, 16 CFR 312.2 and 312.6 (`docs/coppa/coppa-full`).

**BR-coppa-minimization:** The system may collect from a child only what is reasonably necessary for the activity the child is taking part in, and may not make participation depend on giving more. Parental consent does not make over-collection acceptable. Each field collected from or about a child needs a stated purpose. Source: FTC COPPA Rule, 16 CFR 312.7 (`docs/coppa/coppa-full`).

**BR-coppa-retention:** A child's personal information is kept only as long as reasonably necessary for the purposes given in the privacy notice, and never indefinitely. The team must keep a written data retention policy stating the purposes, the business need for keeping the data, and a deletion timeframe, and must publish it in the online privacy notice. Source: FTC COPPA Rule, 16 CFR 312.10 (`docs/coppa/coppa-full`). Flagged — the timeframe itself is not set by the rule and is still undecided (`OI-22`). Development placeholders accepted by the client on 2026-10-28 (Q9): 12 months of inactivity before a child's data is deleted, and 14 days to confirm consent before an unconfirmed account is removed. Both must be configurable, not hardcoded, and may later differ by type of data after testing and legal review.

**BR-coppa-no-third-party-disclosure:** The system must not release a child's personal information to any third party, or make it public in identifiable form, unless the parent has separately consented to that disclosure, apart from the consent to collection and use. Disclosure for money, advertising, or training or developing AI is never treated as necessary to the service. A provider who only supports the system's internal operations may hold the data, but the team must first obtain written assurances that the provider will keep it secure. Source: FTC COPPA Rule, 16 CFR 312.2, 312.5(a)(2) and 312.8(c) (`docs/coppa/coppa-full`). Note: this keeps the product on the email-plus consent path (`BR-coppa-parental-consent`), and it bears on the client's wish for AI recommendation (`OI-2`) if any outside model or vendor would see child data.

**BR-no-reading-level-assessment:** BookBuddies must not assess, estimate, calculate, infer, or assign a child's reading level. There is no in-app reading test. Source: MTG2 flowchart deck, slide 1 ("Design rule") and slide 2; Meeting 2 notes, "Recommendation Algorithm." (v0.2: resolves the v0.1 flag, which assumed an in-app test. The client has reversed that.)

**BR-reading-level-parent-entered:** A reading level is optional. If one is given, the parent/guardian enters it at sign-up using a system they already know (e.g., Lexile, AR/ATOS, DRA, Guided Reading Level, or a grade-level range). If the parent is unsure, the app may show referral links to external resources (e.g., AR Bookfinder, Scholastic Book Wizard) for reference only. Source: MTG2 flowchart deck, slides 2–3. (Meeting 2 notes said "kids asked to find their level externally"; the later deck assigns this to the parent, so the deck governs.)

A team decision, not a rule: the brief notes email is "preferred over phone number for data collection ease." The stated reason is operational convenience, not policy or regulation, so it is recorded as an assumption, `AS-email-linking`, in the specification and in vision-and-scope §2.7, not as a rule.

### 2.2 Parental Oversight and Review

**BR-parent-ultimate-say:** A parent has final authority over which books their child may access but is not required to approve each book the child selects; purchasing a book is treated as implicit approval. Source: client concept brief, "Parental Controls, Privacy, and Account Structure" section; Meeting 2 notes, "Parent and Kid Roles."

**BR-parent-shelf-removal:** A parent may remove books from their child's shelf. When a book is removed, the child receives an in-app notice. Source: Meeting 2 notes, "Parent and Kid Roles" and "Shelf and Notifications."

**BR-parent-rec-not-forced:** A book a parent recommends is added to the child's recommendation list, not placed on the child's shelf. The child may accept or veto it. Source: Meeting 2 notes, "Recommendation Algorithm" and "Parent and Kid Roles."

**BR-child-structured-responses:** A child responds only through predefined, structured choices: Yes, Maybe or No on a recommendation, a reason for "Not for Me" from a fixed list, a rating from a fixed scale, and other predefined options. The child-facing product has no free-text notes, reviews or reflections. Source: client answers 2026-10-28, overall comment 2 and Q8 (`docs/external/client-answers-10-28-2026.md`).

**BR-parent-note:** A parent may add an optional free-text note of at most 250 characters about their child's reading interests, to help BookBuddies make more relevant recommendations. A parent may enter one when setting up the child's profile (`UC-PAR-create-kid-account`) and after confirming the child finished a book (`UC-SHLF-par-finish-book`, team decision 2026-10-29). The note is shown with a prompt telling the parent not to include personal, identifying, sensitive or confidential information such as full names, school names, addresses or contact information. The note is visible to the parent and feeds the recommender, and is never shown to the child. Source: client answers 2026-10-28, overall comment 2 and Q4 (prompt wording from the client).

**BR-notes-visible-to-parent:** *Removed 2026-10-28.* It governed a child's notes and reflections, which no longer exist because children enter no free text (`BR-child-structured-responses`). The identifier is retired and not reused. Original source: Meeting 2 notes, "Book Notes and Privacy."

**BR-24hr-review-window:** *Removed 2026-10-28.* The client confirmed the parent no longer has to confirm review within 24 hours, because the rule was meant for reviewing a child's free-text notes (client answers 2026-10-28, Q10; the answer says "12-hour", taken to mean this rule). No account is suspended for a missed review. The identifier is retired and not reused. Original source: client concept brief, "Parental Controls, Privacy, and Account Structure" section. `OI-16` is closed.

**BR-parent-content-removal:** A parent may remove flagged words or content from their child's account and may report abuse or self-harm signals. Source: client concept brief, "Parental Controls, Privacy, and Account Structure" section.

**BR-parent-report-book:** A parent (Main or Sub Parent) may report a book from a child's recommendation batch under review or from the child's shelf, giving a reason and confirming after a warning that false reports may be punished. Once sent, the report is final and cannot be undone: the book never appears for that child again, and it is removed from their shelf with an in-app notice that gives no reason. The child's rating is kept, even if the system admin later blocks the book; it is deleted only if the book is removed from the system entirely. The report goes to the system admin's list of reported books, where the admin may block the book for everyone or discard the report. A Sub Parent's report is binding on the Main Parent, who is warned of this when creating a Sub Parent account. A false report is handled manually by the admin, who may warn the parent not to send false reports or suspend the account. The reporting parent is not told whether a report was acted on, and neither the child nor the parent is told when a blocked book leaves the shelf. Source: confirmed by the client in conversation with the team, 2026-10-13; no source document records it yet, so cite this entry until one is added.

If it matches, it is flagged for human review by an authorized admin, who decides whether any follow-up is needed. The system takes no automatic action and sends nothing to an outside service or party. Source: client answers 2026-10-28, Q4 and Q6, which replace the Meeting 2 notes, "Book Notes and Privacy" and "Shelf and Notifications," that flagged a child's note to the admin and parents. ### 2.5 Recommendation Computation

**BR-reading-level-proxy:** Recommendations use a child's age and grade as the primary signal. A parent-entered reading level, when present, is one input used to match book difficulty; when it is absent, age and grade stand in for it. Source: Meeting 2 notes, "Recommendation Algorithm"; MTG2 flowchart deck, slide 2.

**BR-similarity-signal-weights:** Similarity between two users for recommendation purposes is computed from a weighted set of behavioral signals only — never from age, location, or other demographic traits — using the following relative weights: saved (+), loved it (++), rated highly (++), recommended to a peer (+++), skipped/ignored (−). Source: BookBuddies Profiles notes, "Recommender" section. Flagged — needs reconfirmation:

Meeting 2 says rating weight should be "kept low, especially early on with small user base," which conflicts with the ++ weights on "loved it" and "rated highly."
"Recommended to a peer" depends on peer sharing, which is deferred (see §2.3).
User-to-user similarity belongs to the collaborative-filtering phase that Meeting 2 deferred until scale allows. Note that the "never from age" clause governs similarity between users only; it does not conflict with BR-reading-level-proxy, which matches books to a child.

**BR-adult-influence-hidden:** When an adult records a private growth/theme note about a child (e.g., "building confidence"), that note may influence which books surface for the child, but the underlying theme or note text must never be shown to the child; the child continues to select only by the quiz criteria visible to them. The parent note of `BR-parent-note` (2026-10-28) is also a parent-written note that feeds the recommender and is never shown to the child, so it may cover this rule. Source: BookBuddies Profiles notes, "Adult Influence" section. Flagged — possibly deferred: Meeting 2 confirmed "direct/bias content controls" as removed from the MVP, which may refer to this feature. Note also that parent book suggestions do carry a note the child sees (MTG2 flowchart deck, slide 1: "I think you will like this because..."); that is a separate, visible note and is not governed by this rule. Confirm with Yang Yang.
